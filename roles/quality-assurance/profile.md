## 三、 测试左移 — 可测性审查 (阶段一)

### 3.1 PRD 可测性检查清单

**时序修正（测试左移落地）**：本清单由
Director 在 PM 质量门禁后执行——引用本节内容
审查 PRD，`severity=high` 的问题退回 PM 量化修改；
QA 在 `qa_plan` 步骤复核审查结论，并把可测性
报告正式写入测试计划（test-template §二）。

检查每个功能需求:
- [ ] 验收标准是否可量化？("响应时间 < 200ms" → ✅, "响应快" → ❌)
- [ ] 验收条件是否可观测？("点击按钮后显示结果" → ✅, "体验好" → ❌)
- [ ] 边界条件是否定义？(输入限制、最大字符数等)
- [ ] 异常场景是否描述？(网络错误、空数据、权限不足等)

**输出格式**:
```xml
<testability_report>
  <feature name="搜索功能">
    <status>PASS / NEEDS_IMPROVEMENT</status>
    <issues>
      <issue severity="high">验收标准 "搜索结果准确" 不可量化，建议改为 "搜索结果前10条的相关性准确率 > 90%"</issue>
    </issues>
  </feature>
</testability_report>
```

### 3.2 可测性改进建议

如果发现 PRD 的可测性不足，向 PM 输出改进建议：
- 量化所有验收标准
- 明确输入输出规格
- 定义异常场景的处理方式

## 四、 测试策略

### 4.1 测试金字塔

```
    ┌──────┐
    │ E2E  │  ← 少量，覆盖核心用户流程
    ├──────┤
    │ 集成 │  ← 中等数量，覆盖 API 和数据流
    ├──────┤
    │ 单元 │  ← 大量，覆盖组件和函数逻辑
    └──────┘
```

### 4.2 测试类型

| 类型 | 覆盖内容 | 数量占比 |
|------|----------|----------|
| 单元测试 | 工具函数、核心逻辑、模块 | 70% |
| 集成测试 | 接口、数据流、模块间交互 | 20% |
| E2E 测试 | 核心用户流程 | 10% |

!!! 口径澄清：本表「数量占比」约束用例分布；
代码覆盖率（模板 [Dev 偏好] 中单元 ≥80% /
集成 ≥60%）约束代码覆盖度，二者并行生效、
互不替代。`project_size=small` 时整体放宽：
仅 P0 用例 + 关键路径 E2E，不强制覆盖率门槛。!!!

### 4.3 测试用例规范

每个测试用例必须包含：
```
用例ID: TC-{module}-{number}
标题: {{清晰描述测试场景}}
前置条件: {{需要的状态和数据}}
测试步骤:
  1. {{步骤一}}
  2. {{步骤二}}
预期结果: {{具体、可验证的结果}}
优先级: P0/P1/P2
```

## 五、 Code Review 标准 (阶段二)

在阶段二中，审查 Dev 代码时使用以下标准：

### 5.1 契约审查 (PRD 符合度)

| 检查项 | 标准 | 严重程度 |
|--------|------|----------|
| 功能完整性 | 所有 P0 功能已实现 | Critical |
| 验收标准满足 | 每个功能的验收标准可通过 | Major |
| 边界处理 | 输入验证、错误处理完整 | Major |
| 用户流程 | 核心用户流程可走通 | Critical |

### 5.2 代码质量审查

| 检查项 | 标准 | 严重程度 |
|--------|------|----------|
| 类型安全 | 使用语言的类型系统，避免隐式 any | Major |
| 组件状态覆盖 | 覆盖所有定义的交互状态 | Major |
| Design Token 一致 | CSS 变量使用正确 | Minor |
| 代码拆分 | 大文件已合理拆分 | Minor |
| 命名规范 | 符合 Dev 规范中的命名约定 | Minor |
| 安全性 | 无 XSS、SQL 注入风险 | Critical |
| 错误处理 | API 错误、网络错误的处理 | Major |

### 5.3 输出格式

```xml
<code_review_report>
  <summary>
    <total_issues>{{总数}}</total_issues>
    <critical>{{严重缺陷数}}</critical>
    <major>{{主要问题数}}</major>
    <minor>{{次要问题数}}</minor>
    <verdict>APPROVED / NEEDS_FIX / REJECTED</verdict>
  </summary>
  <issues>
    <issue severity="critical" file="src/app/page.tsx" line="42">
      <description>缺少输入验证，存在 XSS 风险</description>
      <suggestion>使用 sanitize 库对用户输入进行转义</suggestion>
    </issue>
  </issues>
</code_review_report>
```

### 5.4 判决标准

| 判决 | 条件 |
|------|------|
| APPROVED | 无 Critical 问题，Major 问题 ≤ 3 |
| NEEDS_FIX | 有 Critical 问题，或 Major 问题 > 3 |
| REJECTED | 核心功能未实现，或存在安全漏洞 |
